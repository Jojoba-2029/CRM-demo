# Решения и допущения

Что решено там, где ТЗ не даёт однозначного ответа.

## Роли и пользователи

- Роль хранится в таблице `profiles`. Профиль создаётся триггером при создании пользователя в Supabase Auth. Роль берётся из `app_metadata.role`: это поле меняет только администратор, сам пользователь — нет. По умолчанию роль — «Исполнитель». Постановщика назначают SQL-запросом (см. README).
- Через API роль изменить нельзя никому. Привилегий на изменение `profiles` у пользователей нет.
- Исполнитель видит свой профиль и профили постановщиков: они нужны, чтобы показать автора задачи и автора записей истории. Список других исполнителей ему недоступен.

## Задачи

- Исполнителем задачи может быть только пользователь с ролью «Исполнитель». Это проверяет база.
- Постановщик редактирует название, описание, исполнителя и объект задачи в любом статусе, кроме «Принята». Принятая задача заморожена. Её можно только удалить.
- Смена исполнителя не сбрасывает статус и не пишется в историю статусов: история фиксирует только смены статусов, как в ТЗ.
- Принять задачу или вернуть её на доработку может любой постановщик, не только автор: в ТЗ постановщик «видит всё».
- Комментарий обязателен только при возврате на доработку. Пробелы комментарием не считаются. В интерфейсе комментарий запрашивается только для этого перехода, хотя база принимает необязательный комментарий и для остальных.
- Статус меняется только через функцию `change_task_status`. Прямое изменение колонки `status` запрещено всем, включая постановщика: колонке не выдана привилегия, плюс есть страховочная проверка в триггере.
- Создание задачи тоже записывается в историю (переход «— → Новая»), так история полная.
- Автор, дата создания и статус новой задачи всегда проставляются базой, значения от клиента игнорируются или отклоняются.

## Удаление

- Удаление объекта удаляет его задачи вместе с историей (каскадно). В интерфейсе перед этим показывается подтверждение с количеством задач.
- Удаление задачи удаляет её историю. Удалить или изменить отдельные записи истории нельзя. Удаление задачи целиком доступно только постановщику — это осознанное допущение: иначе удалённая задача оставляла бы «висящую» историю.

## Ошибки

- Функция смены статуса возвращает коды, которые Supabase превращает в HTTP-статусы: 403 — переход недоступен, 404 — задача не найдена или чужая (чужую задачу исполнитель не отличает от несуществующей), 400 — нет комментария, 409 — попытка изменить принятую задачу.

## Инструменты

- Пакетный менеджер — Yarn 4 через Corepack. Пакеты моложе суток Yarn не ставит (`npmMinimalAgeGate`), это оставлено включённым.
- TypeScript 7 (нативный компилятор): тот же движок использует линтер Oxlint в режиме проверки по типам, поэтому `yarn typecheck` и `yarn lint` не расходятся. Ограничение: в TypeScript 7 нет классического JS API (`require('typescript')`), поэтому инструменты, которым он нужен (typescript-eslint, `vitest --typecheck`, ts-morph), с ним не заработают.
- Форматирование — Oxfmt (тот же набор Oxc, что и линтер). Стиль совместим с Prettier: ширина строки 100, двойные кавычки, точки с запятой, LF. `yarn db:types` форматирует сгенерированные типы сразу после генерации, чтобы они не ломали `yarn format:check`.
- Минимальная версия Node задана в `package.json` (`engines`) и `.node-version`. Yarn 4 сам `engines` не проверяет, поэтому это делает `scripts/check-node.mjs` при установке и перед `dev`/`build`; он же следит, чтобы оба значения совпадали.

## Что не сделано

- Деплой и облачный проект Supabase: нужны аккаунты, всё описано в README.
- Управление пользователями из интерфейса — пользователи создаются в панели Supabase.
- Пагинация и поиск по спискам: при объёме тестового задания не нужны.
- Обновление данных в реальном времени (Supabase Realtime): изменения видны после перехода по страницам или обновления.
- E2E-тесты интерфейса. Безопасность покрыта тестами на уровне базы, логика кнопок — unit-тестами.
