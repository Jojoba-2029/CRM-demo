# Деплой: GitHub Pages + GitHub Actions + Supabase

Приложение работает в интернете бесплатно на трёх сервисах:

```
браузер ──► GitHub Pages (статический фронтенд: HTML/JS/CSS)
               │
               └──► Supabase (Postgres + RLS, Auth, REST API)
```

| Сервис             | Что делает                                                              | Бесплатно                                                                                                        |
| ------------------ | ----------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **GitHub Pages**   | Хостит собранный фронтенд по адресу `https://<owner>.github.io/<repo>/` | Для публичных репозиториев                                                                                       |
| **GitHub Actions** | Проверки, миграции базы, сборка и публикация                            | Для публичных репозиториев минуты не ограничены                                                                  |
| **Supabase Free**  | База данных, правила доступа, вход пользователей                        | Да. Проект «засыпает» после 7 дней без запросов — перед показом откройте его в панели Supabase и нажмите Restore |

Своего сервера нет: фронтенд — набор статических файлов, а вся логика и защита данных работают в Supabase.

## Что подключено в репозитории

| Файл                                                    | Назначение                                                                                                                                                              |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `.github/workflows/ci.yml`                              | Проверки на каждый пуш в `dev` и на каждый PR: форматирование, типы, линтер, unit-тесты, сборка и тесты безопасности базы (pgTAP на локальном Supabase прямо в Actions) |
| `.github/workflows/deploy.yml`                          | Деплой на пуш в `main` или вручную: проверки → миграции в облачный Supabase → сборка → публикация на GitHub Pages                                                       |
| `.github/actions/setup/action.yml`                      | Общая подготовка: Node из `.node-version`, Yarn 4 через Corepack, кэш и установка зависимостей                                                                          |
| `vite.config.ts` (`base`) и `src/main.tsx` (`basename`) | Сайт на Pages открывается из подпапки `/<repo>/`: путь передаёт workflow через `BASE_PATH`, локально — корень `/`                                                       |
| `dist/404.html` (создаётся при деплое)                  | Копия `index.html`: Pages отдаёт его на любой неизвестный путь, поэтому прямые ссылки вроде `/CRM-demo/tasks/…` открывают приложение                                    |

`vercel.json` и `public/_redirects` остались для запасного варианта — деплоя на Vercel или Netlify. На GitHub Pages они ни на что не влияют.

## Порядок деплоя

```
push в main ──► Проверки (ci.yml) ──► Миграции Supabase ──► Сборка ──► Публикация на Pages
```

- Если проверки не прошли, база и сайт не трогаются.
- `supabase db push` применяет **только новые** файлы из `supabase/migrations`. Уже применённые миграции Supabase помнит в своей таблице истории.
- `supabase/seed.sql` в облаке автоматически **не** запускается, иначе он пересоздавал бы данные на каждом деплое. Тестовые данные загружаются один раз вручную (шаг 6 ниже).
- Повторный деплой без изменений безопасен: новых миграций нет, сайт просто пересобирается.

## Однократная настройка

### 1. Репозиторий

- Репозиторий должен быть **публичным**: на бесплатном тарифе GitHub Pages работает только с публичными.
- **Settings → Pages → Build and deployment → Source:** выберите **GitHub Actions**.

### 2. Данные из Supabase

| Что             | Где взять                                                                                             |
| --------------- | ----------------------------------------------------------------------------------------------------- |
| Project ref     | Адрес проекта в панели: `supabase.com/dashboard/project/<ref>`                                        |
| Project URL     | **Connect** или **Project Settings → API Keys**: `https://<ref>.supabase.co`                          |
| Publishable key | Там же: `sb_publishable_…` (или legacy `anon`). Ключ публичный, его можно отдавать во фронтенд        |
| Access token    | **Account → Access Tokens → Generate new token** (supabase.com/dashboard/account/tokens)              |
| Пароль базы     | Задаётся при создании проекта. Если забыт — **Project Settings → Database → Reset database password** |

Secret key (`sb_secret_…`, бывший `service_role`) **не нужен нигде**. Не добавляйте его ни в репозиторий, ни в настройки Actions.

### 3. Secrets и variables в GitHub

**Settings → Environments → `github-pages`** (окружение создаётся автоматически, когда в Settings → Pages выбран источник GitHub Actions). Там в блоках **Environment secrets** и **Environment variables** добавьте значения ниже.

Почему окружение, а не уровень репозитория: деплойные job-ы (`migrate`, `build`, `deploy`) привязаны к окружению `github-pages`, а оно по умолчанию разрешает только ветку `main`. Поэтому пароль базы и токен недоступны workflow из других веток и PR. Значения, заданные на уровне репозитория (**Settings → Secrets and variables → Actions**), тоже сработают, но защищены слабее.

| Имя                      | Тип        | Значение                                                      |
| ------------------------ | ---------- | ------------------------------------------------------------- |
| `SUPABASE_ACCESS_TOKEN`  | **Secret** | Access token Supabase — нужен для `supabase link` и `db push` |
| `SUPABASE_DB_PASSWORD`   | **Secret** | Пароль базы                                                   |
| `SUPABASE_PROJECT_REF`   | Variable   | Project ref                                                   |
| `VITE_SUPABASE_URL`      | Variable   | Project URL                                                   |
| `VITE_SUPABASE_ANON_KEY` | Variable   | Publishable key                                               |

`VITE_*` — обычные variables, а не secrets: Vite всё равно встраивает их в публичный JS-бандл. Если чего-то не хватает, деплой остановится с сообщением, что именно не задано.

### 4. Настройки Supabase Auth

- **Authentication → Sign In / Providers:** выключите **Allow new users to sign up** и нажмите **Save changes** (п. 3.5 ТЗ). `supabase/config.toml` настраивает только локальный Supabase, в облаке это делается руками.
- **Authentication → URL Configuration → Site URL:** `https://<owner>.github.io/<repo>/`.

### 5. Первый деплой

Запушьте в `main` или запустите вручную: **Actions → Deploy → Run workflow**. После успешного запуска в **Table Editor** Supabase появятся таблицы `profiles`, `objects`, `tasks`, `task_status_history`, а адрес сайта будет виден в шаге «Публикация».

### 6. Тестовые данные (один раз)

1. **Supabase → SQL Editor → New query**, вставьте содержимое `supabase/seed.sql`.
2. **Прямо в редакторе** замените `Password123!` на свой пароль: локальный пароль опубликован в README и для публичного демо не годится.
3. Нажмите **Run**. Появятся 1 постановщик (`manager@crm.local`), 2 исполнителя (`executor1@crm.local`, `executor2@crm.local`), 3 объекта и 6 задач во всех статусах. Все названия и адреса выдуманные.

Повторный запуск seed упадёт на дублях: данные уже есть. Чтобы загрузить их заново, сначала удалите тестовых пользователей в **Authentication → Users** (их задачи и объекты удалите в Table Editor).

## Если что-то пошло не так

| Симптом                                             | Причина и решение                                                                                                                                                                                                             |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Деплой упал на «Проверить настройки»                | Не задан secret или variable из шага 3 — имя указано в логе. Re-run повторяет старый коммит: если менялся сам workflow, нужен новый пуш в `main`                                                                              |
| Упал шаг «Привязать проект» / «Применить миграции»  | Неверный access token, пароль базы или project ref; или проект Supabase на паузе — нажмите Restore в панели                                                                                                                   |
| Шаг «Публикация»: _Branch is not allowed to deploy_ | В **Settings → Environments → github-pages** разрешите ветку `main`                                                                                                                                                           |
| Сайт открылся, но вход не проходит                  | Не загружен seed (шаг 6) или в `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` указан другой проект                                                                                                                            |
| После входа «Профиль не найден»                     | Пользователь создан до применения миграций: удалите его и создайте заново (профиль создаёт триггер из миграции)                                                                                                               |
| Белая страница, в консоли 404 на `/assets/…`        | Сборка сделана без `BASE_PATH`. Через `deploy.yml` он подставляется сам, вручную: `BASE_PATH=/CRM-demo/ yarn build` (в Git Bash на Windows — с `MSYS_NO_PATHCONV=1`, иначе путь превратится в `/Program Files/Git/CRM-demo/`) |

## Проверить сборку для Pages локально

```bash
MSYS_NO_PATHCONV=1 BASE_PATH=/CRM-demo/ yarn build
```

```bash
yarn vite preview --base /CRM-demo/
```

Откройте `http://localhost:4173/CRM-demo/`. Сборка берёт ключи из `.env.local`, то есть работает с локальным Supabase. `MSYS_NO_PATHCONV` нужен только в Git Bash, в PowerShell задайте переменную через `$env:BASE_PATH = "/CRM-demo/"`.
